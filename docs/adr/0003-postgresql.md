# ADR-003：使用 PostgreSQL 作为主数据库

- 状态：Accepted
- 日期：2026-11-22
- 决策者：项目所有者

## 背景

当前项目配置使用 `mysql+asyncmy`，数据模型仍处于早期阶段，尚未完成用户、计划版本、任务、跟进、画像洞察和通知等完整迁移。

MyJARVIS 需要结构化计划快照、严格约束、可靠任务领取和后续长期记忆检索能力。

## 决策

从 P2 起使用 PostgreSQL 16 作为主数据库，并通过 SQLAlchemy 2.x async 与 `asyncpg` 访问。

继续使用 Alembic 管理全部结构迁移。

## 选择理由

- `JSONB` 适合保存计划版本快照、结构化工具参数和审计数据。
- 外键、部分唯一索引和复杂约束更适合多用户及计划生命周期。
- `SELECT ... FOR UPDATE SKIP LOCKED` 适合可靠领取通知和后台任务。
- 后续可以使用 `pgvector` 在同一数据库中实现基于证据的长期记忆。
- Testcontainers、托管数据库和 PostgreSQL 工具生态成熟。
- 当前项目还未形成稳定生产数据，现在迁移成本较低。

## 备选方案

### 继续使用 MySQL

可以完成当前 MVP，但后续语义检索通常需要额外部署 Qdrant 等向量服务，并且 JSON 查询和部分索引能力的选择空间较小。

### SQLite

适合单元测试和快速原型，不适合作为带多用户、后台 Worker 和并发通知任务的生产主数据库。

## 数据迁移规则

- 如果当前数据库中只有测试数据，在 P2 创建新的 PostgreSQL 数据库并重建结构。
- 如果存在必须保留的数据，先备份和导出，再编写单独的数据迁移脚本。
- 不能在未确认数据价值的情况下直接删除或重建现有数据库。
- 所有表结构变更必须通过新的 Alembic revision。

## 后果和代价

- 本地开发、CI 和生产都需要运行 PostgreSQL。
- 现有 MySQL 配置和迁移需要替换。
- P1/P2 需要额外完成数据库容器、迁移和测试数据库设置。
- `pgvector` 属于后续扩展，不应在 MVP 首版迁移中提前引入未使用的向量字段。

## 验证方式

- 空数据库可以按顺序执行全部迁移。
- 测试使用独立 PostgreSQL 实例。
- 并发任务领取测试不会重复处理同一任务。
- 回退迁移能够在测试数据库执行。

## 后续待办

- 在 P1 加入 PostgreSQL Docker 服务。
- 在 P2 重建迁移基线。
- 确认现有数据库数据的保留或清理策略。
