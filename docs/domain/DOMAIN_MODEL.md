# MyJARVIS 领域模型

本文件定义 MyJARVIS 的业务名词、对象职责、对象关系和必须始终成立的业务规则。

此阶段描述的是业务模型，不规定数据库表、字段类型、索引、API 地址或框架实现。状态枚举将在后续生命周期设计中进一步细化。

## 1. 领域术语

| 领域术语 | 代码名称 | 定义 | 不等于或容易混淆的内容 |
|---|---|---|---|
| 用户 | `User` | 登录系统并拥有个人数据的账号主体 | 不是一次聊天，也不是某个计划 |
| 用户画像 | `UserProfile` | 用户当前生效的求职方向、目标岗位、技能、时间约束等信息的汇总视图 | 不是未经确认的模型推断 |
| 画像事实 | `ProfileFact` | 画像中一条有来源、可确认、可追溯的信息 | 不是整份画像，也不是普通聊天消息 |
| 候选洞察 | `ProfileInsight` | 系统根据多条对话、任务和跟进记录形成的待确认行为规律或偏好假设 | 不是正式画像事实，也不是性格诊断 |
| 洞察证据 | `InsightEvidence` | 候选洞察与一条真实业务记录之间的关联，记录支持或矛盾以及引用依据 | 不是原始消息本身，也不是模型编造的解释 |
| 目标 | `Goal` | 用户希望达到的结果及其时间、范围等约束 | 不是具体执行步骤 |
| 计划 | `Plan` | 为实现一个目标而建立的长期执行容器 | 不是某一时刻的不可变快照 |
| 计划版本 | `PlanVersion` | 计划在一次确认或调整后形成的不可变结构快照 | 不能被后续修改原地覆盖 |
| 里程碑 | `Milestone` | 计划中一个有独立价值、可衡量的阶段结果 | 不是用户直接执行的最小动作 |
| 任务 | `Task` | 用户可以执行和汇报进度的最小工作项 | 不是整个阶段，也不是聊天中的一句建议 |
| 任务依赖 | `TaskDependency` | 两个任务之间必须满足的先后关系 | 不代表日历上的重复任务 |
| 跟进记录 | `CheckIn` | 用户在一次主动反馈中提交的完整执行情况 | 不是任务当前状态本身 |
| 任务更新 | `TaskUpdate` | 某次跟进中针对一个任务提交的状态和进度变化 | 不是任务当前字段的简单覆盖 |
| 计划变更建议 | `PlanChangeProposal` | 尚未生效的结构调整方案及其差异 | 批准前不是正式计划版本 |
| 复盘 | `Review` | 针对明确时间范围和计划版本生成的结构化总结 | 不是模型对全部聊天记录的随意总结 |
| 会话 | `Conversation` | 一段连续聊天上下文 | 不是目标或计划，也不保存执行事实的唯一副本 |
| 消息 | `Message` | 用户或 Agent 在会话中产生的一条内容 | 不能直接代替进度或审批记录 |
| 资料来源 | `Source` | 搜索结果或外部资料中的标题、链接、引用片段等 | 不是模型自行生成的无来源内容 |
| 跟进安排 | `FollowUpSchedule` | 用户确认的提醒时间、节奏、时区和渠道偏好 | 不是一次已经发送的通知 |
| 通知投递 | `NotificationDelivery` | 一次提醒的实际发送记录和结果 | 不负责决定计划内容 |
| Agent 执行 | `AgentRun` | 一次 Agent 处理上下文、调用模型和工具的过程 | 不是一条聊天消息 |
| 工具调用 | `ToolCall` | Agent 对某个受控工具执行的一次请求 | 不允许绕过后端校验直接操作数据 |

用户、Agent 和定时任务系统是行为参与者，不是同一类业务实体。Agent 是受后端约束的系统执行者，不能代替用户确认关键变化。

## 2. 核心对象及职责

| 对象 | 核心职责 | 不应承担的事情 | 所有者 |
|---|---|---|---|
| `User` | 标识账号并提供业务数据的所有权边界 | 保存具体计划内容 | 自身 |
| `UserProfile` | 展示用户当前生效的画像信息 | 保存未经确认的推断或被删除的事实 | `User` |
| `ProfileFact` | 保存画像信息的值、来源和确认历史 | 直接决定计划如何执行 | `User` |
| `ProfileInsight` | 保存带证据、评分和确认过程的候选个性化规律 | 未经确认进入正式画像或直接修改关键计划条件 | `User` |
| `InsightEvidence` | 连接候选洞察与真实业务证据，并标明支持或矛盾方向 | 保存没有真实来源的模型解释 | `ProfileInsight` |
| `Goal` | 描述用户最终想达到的结果和约束 | 保存每天的具体任务 | `User` |
| `Plan` | 组织实现目标的长期方案和当前版本 | 原地覆盖历史计划 | `User` |
| `PlanVersion` | 保存一次确认后的不可变计划快照 | 被后续修改直接覆盖 | `Plan` |
| `Milestone` | 表示一个有价值的阶段结果 | 表示用户直接执行的最小动作 | `Plan` |
| `Task` | 表示可以执行、跟进和汇报进度的最小工作项 | 保存完整聊天上下文或计划历史 | `Plan` |
| `TaskDependency` | 控制任务之间的先后顺序 | 连接不同用户或不同计划的任务 | `Plan` |
| `CheckIn` | 保存用户一次完整的执行反馈 | 代替任务当前状态 | `Plan` |
| `TaskUpdate` | 作为任务状态和进度变化的历史证据 | 被静默修改或删除 | `CheckIn` |
| `PlanChangeProposal` | 保存尚未生效的计划调整建议 | 批准前修改生效计划 | `Plan` |
| `Review` | 基于明确范围生成结构化复盘 | 编造没有执行记录支持的事实 | `Plan` |
| `Conversation` | 保存上下文和交互过程 | 作为目标和任务的唯一真实来源 | `User` |
| `Message` | 保存一次对话内容 | 直接触发高权限操作 | `Conversation` |
| `Source` | 保存外部资料的引用依据 | 被当作可信业务指令 | 引用它的消息或工具调用 |
| `FollowUpSchedule` | 保存跟进节奏和通知偏好 | 负责发送实际通知 | `Plan` |
| `NotificationDelivery` | 记录一次通知的发送结果 | 决定任务是否完成 | `FollowUpSchedule` |
| `AgentRun` | 记录一次 Agent 执行过程 | 代替业务审批 | `User` |
| `ToolCall` | 记录一次受控工具的请求和结果 | 绕过权限与参数校验 | `AgentRun` |

### 2.1 行为参与者

| 参与者 | 权限边界 |
|---|---|
| 访客 | 只能注册和登录，不能调用模型或访问业务数据 |
| 已登录用户 | 管理自己的画像、目标、计划、任务、跟进和复盘，批准关键变化 |
| Agent | 读取当前用户上下文，生成草稿，调用允许的工具，提出变更建议 |
| 定时任务系统 | 根据生效计划和用户偏好触发跟进，不负责审批计划 |
| 管理员 | MVP 不实现 |

## 3. 对象关系图

### 3.1 核心业务关系

```text
User 1 ───── 1 UserProfile
User 1 ───── N Goal
User 1 ───── N Conversation

UserProfile 1 ───── N ProfileFact
User 1 ───── N ProfileInsight

ProfileInsight N ───── N Message / CheckIn / TaskUpdate
               经由 InsightEvidence
ProfileInsight 0..1 ───── 1 ProfileFact

Goal 1 ───── N Plan
Plan 1 ───── N PlanVersion
Plan 1 ───── N Milestone
Milestone 1 ───── N Task
Plan 1 ───── N Task

Task N ───── N Task
       经由 TaskDependency

Plan 1 ───── N CheckIn
CheckIn 1 ───── N TaskUpdate
Task 1 ───── N TaskUpdate

Plan 1 ───── N PlanChangeProposal
Plan 1 ───── N Review
Review 0..N ───── ProfileInsight

Conversation 1 ───── N Message
Message 1 ───── N Source

Plan 1 ───── N FollowUpSchedule
FollowUpSchedule 1 ───── N NotificationDelivery

AgentRun 1 ───── N ToolCall
```

### 3.2 关系说明

- 一个用户拥有一份当前画像，但画像中的事实可以有多条历史记录。
- 一个用户可以拥有多个目标，每个目标拥有一个或多个计划。
- 同一目标同一时间最多只有一个生效计划。
- 重新规划同一个目标时，优先创建新的 `PlanVersion`，而不是同时激活多套计划。
- 一个计划包含多个版本、里程碑、任务、跟进记录、变更建议和复盘。
- 每个任务归属于一个里程碑，同时也能被验证为属于该里程碑所在的计划。
- `TaskDependency` 是有向关系，指向被依赖的前置任务和依赖它的后续任务。
- 一次 `CheckIn` 可以包含多个 `TaskUpdate`，但同一任务在同一次跟进中最多只有一条有效更新。
- 每个 `Review` 使用一个明确时间范围，并引用该范围内实际生效的计划版本。
- `Review` 可以触发候选 `ProfileInsight`，但复盘状态和画像洞察状态相互独立。
- `ProfileInsight` 必须通过 `InsightEvidence` 关联真实的对话、跟进或任务记录，并区分支持证据和矛盾证据。
- 用户确认候选洞察后，可以创建或更新一个正式 `ProfileFact`；未确认的洞察不能进入当前画像。
- 会话消息可以引用搜索结果，但 `Source` 不直接决定任务进度或计划结构。

## 4. 每个对象的关键属性

以下是业务属性，不代表最终数据库字段设计。

### 4.1 `User`

| 属性 | 含义 | 要求 |
|---|---|---|
| 用户标识 | 唯一标识用户 | 必须 |
| 登录标识 | 用于注册和登录的邮箱或其他身份 | 必须 |
| 显示名称 | 界面上展示的名称 | 可选 |
| 账号状态 | 是否可登录、是否停用 | 必须 |
| 时区 | 用户默认时区 | 必须，默认使用用户设置 |
| 创建时间、更新时间 | 账号生命周期记录 | 系统生成 |

### 4.2 `UserProfile`

| 属性 | 含义 | 要求 |
|---|---|---|
| 所属用户 | 画像所有者 | 必须 |
| 求职方向 | 例如数据分析、后端开发 | 可逐步补充 |
| 目标岗位 | 当前主要求职岗位 | 可逐步补充 |
| 当前技能 | 已掌握或正在学习的技能摘要 | 可逐步补充 |
| 当前求职阶段 | 例如准备中、投递中、面试中 | 可选 |
| 每周可投入时间 | 用户能稳定投入的时间 | 关键信息 |
| 当前画像版本或更新时间 | 帮助判断画像是否仍有效 | 系统生成 |

`UserProfile` 是当前有效信息的汇总视图；`ProfileFact` 提供每条信息的来源和确认历史。两者必须保持同步，不能让画像显示未经确认的事实。

### 4.3 `ProfileFact`

| 属性 | 含义 | 要求 |
|---|---|---|
| 所属用户 | 信息所有者 | 必须 |
| 信息类别 | 技能、目标、时间、经验等 | 必须 |
| 信息键和值 | 例如“每周投入时间 = 8 小时” | 必须 |
| 信息来源 | 用户直接填写、对话提取或 Agent 建议 | 必须 |
| 确认状态 | 待确认、已确认、已拒绝、已失效 | 必须 |
| 生效时间和失效时间 | 表达用户情况的历史变化 | 可选 |
| 创建时间、更新时间 | 追溯信息来源 | 系统生成 |

未确认的敏感推断不能计入正式画像。

### 4.4 `ProfileInsight`

| 属性 | 含义 | 要求 |
|---|---|---|
| 所属用户 | 候选规律所有者 | 必须 |
| 个性化维度 | 例如任务长度、提醒时间、计划详细程度 | 必须 |
| 结构化结论 | 带适用条件的可观察规律 | 必须 |
| 适用范围 | 仅当前目标、某类计划或长期偏好 | 必须 |
| 支持证据 | 支持该规律的 `Message`、`CheckIn` 或 `TaskUpdate` | 至少满足评分门槛 |
| 矛盾证据 | 与规律不一致的真实记录 | 有则必须保存 |
| 证据分和评分明细 | 确定性规则计算出的总分及各维度得分 | 达到确认门槛时必须 |
| 来源复盘 | 哪次 `Review` 触发了候选规律 | 可选 |
| 状态 | 候选、已支持、待确认、用户确认、拒绝、过期或替代 | 必须 |
| 最近提示时间 | 控制询问冷却期 | 已提示时记录 |
| 对应画像事实 | 用户确认后生成的 `ProfileFact` | 确认后记录 |
| 创建、最后验证和过期时间 | 管理洞察时效 | 系统生成或规则计算 |

`ProfileInsight` 只能描述可观察的行为和适用条件。例如“用户在 30～45 分钟任务中的完成率更高”，不能写成“用户缺乏自律”等身份评价。

LLM 可以发现候选规律并关联证据，但证据分必须由确定性规则计算。模型自行输出的置信度不能直接作为业务分数。

#### 4.4.1 `InsightEvidence`

| 属性 | 含义 | 要求 |
|---|---|---|
| 所属洞察 | 这条证据用于支持或反驳哪条候选规律 | 必须 |
| 证据类型 | `Message`、`CheckIn`、`TaskUpdate` 或其他受支持事件 | 必须 |
| 证据标识 | 指向具体业务记录 | 必须 |
| 证据方向 | 支持该规律或与规律矛盾 | 必须 |
| 引用快照 | 当时实际使用的内容摘要或数值 | 必须 |
| 关联时间 | 该证据发生或被发现的时间 | 必须 |

一条 `ProfileInsight` 至少应有支持证据才能形成有意义的候选结论；存在矛盾记录时，矛盾证据也必须保存。洞察与证据必须属于同一用户。

### 4.5 `Goal`

| 属性 | 含义 | 要求 |
|---|---|---|
| 所属用户 | 目标所有者 | 必须 |
| 标题 | 简短名称 | 必须 |
| 期望结果 | 用户最终想达到的状态 | 必须 |
| 约束 | 时间、方向、预算或其他限制 | 可选 |
| 开始日期、截止日期 | 目标周期 | 按场景使用 |
| 状态 | 当前目标所处阶段 | 必须 |
| 创建时间、更新时间 | 目标生命周期记录 | 系统生成 |

目标范围发生实质变化时，应评估创建新目标，而不是只修改一个任务。

### 4.6 `Plan`

| 属性 | 含义 | 要求 |
|---|---|---|
| 所属用户和 `Goal` | 明确所有权和存在目的 | 必须 |
| 当前生效版本 | 用户当前执行所依据的 `PlanVersion` | 生效后必须 |
| 状态 | 草稿、生效、完成、取消或归档 | 必须 |
| 创建时间、更新时间 | 计划生命周期记录 | 系统生成 |

`Plan` 是长期容器，不原地保存历史快照。

### 4.7 `PlanVersion`

| 属性 | 含义 | 要求 |
|---|---|---|
| 所属 `Plan` | 版本所属计划 | 必须 |
| 版本号 | 按计划内递增 | 必须 |
| 计划结构快照 | 里程碑、任务、预计时间、依赖等结构 | 必须 |
| 基准版本 | 本次基于哪个版本产生 | 首次版本可为空 |
| 变更类型 | 首次确认、自动调整、批准变更、人工编辑 | 必须 |
| 变更原因 | 为什么产生此版本 | 自动调整和关键变更必须 |
| 创建者 | 用户、Agent 或系统 | 必须 |
| 确认状态和确认时间 | 是否已经成为生效版本 | 必须 |
| 创建时间 | 版本形成时间 | 系统生成 |

计划版本确认后，其结构快照不可原地修改。

### 4.8 `Milestone`

| 属性 | 含义 | 要求 |
|---|---|---|
| 所属计划和用户 | 业务归属 | 必须 |
| 标题和阶段结果 | 这个阶段需要交付什么价值 | 必须 |
| 完成标准 | 如何判断阶段完成 | 必须 |
| 顺序 | 在计划中的先后位置 | 必须 |
| 目标日期 | 预期完成时间 | 可选 |
| 状态 | 当前执行状态 | 必须 |

### 4.9 `Task`

| 属性 | 含义 | 要求 |
|---|---|---|
| 稳定任务标识 | 跨计划版本追踪同一任务 | 必须 |
| 所属用户、计划和里程碑 | 业务归属与层级 | 必须 |
| 标题和说明 | 用户具体要做什么 | 标题必须 |
| 预计用时 | 用于排期和计算加权进度 | 尽量必填 |
| 截止时间 | 任务必须完成的时间 | 可选 |
| 优先级 | 处理先后顺序 | 可选 |
| 状态 | 未开始、进行中、受阻、已完成等 | 必须 |
| 当前进度 | 来自最近一次有效 `TaskUpdate` 的结果 | 必须 |
| 创建时间、更新时间 | 任务生命周期记录 | 系统生成 |

任务状态和进度属于当前执行状态，不能覆盖历史 `TaskUpdate`。

### 4.10 `TaskDependency`

| 属性 | 含义 | 要求 |
|---|---|---|
| 前置任务 | 必须先完成或推进的任务 | 必须 |
| 后续任务 | 依赖前置任务的任务 | 必须 |
| 依赖类型 | MVP 只支持完成后才能开始 | 必须 |
| 创建者 | 用户或 Agent | 必须 |

前置任务和后续任务必须属于同一用户和同一计划，且不能形成循环。

### 4.11 `CheckIn`

| 属性 | 含义 | 要求 |
|---|---|---|
| 所属用户和计划 | 反馈归属 | 必须 |
| 反馈时间 | 用户实际提交反馈的时间 | 必须 |
| 当前可用时间 | 用户下一次或本周可投入时间 | 可选 |
| 阻碍说明 | 用户遇到的问题 | 可选 |
| 来源提醒 | 由哪个跟进安排触发 | 可选 |
| 提交时间 | 系统接收到反馈的时间 | 系统生成 |

已提交的跟进记录作为历史证据保存；如需纠正，应追加修正记录，而不是静默覆盖。

### 4.12 `TaskUpdate`

| 属性 | 含义 | 要求 |
|---|---|---|
| 所属 `CheckIn` 和 `Task` | 更新来源与目标 | 必须 |
| 用户报告的状态 | 已完成、部分完成、未开始、受阻 | 必须 |
| 用户报告的进度 | 0%～100% | 部分完成时必填 |
| 备注 | 用户对本次更新的说明 | 可选 |
| 记录时间 | 系统接收时间 | 系统生成 |

`TaskUpdate` 是计算任务进度和生成复盘的历史证据。

### 4.13 `PlanChangeProposal`

| 属性 | 含义 | 要求 |
|---|---|---|
| 所属计划和基准版本 | 本次调整基于什么计划 | 必须 |
| 变更内容 | 修改前和修改后的结构差异 | 必须 |
| 风险等级 | 自动执行或必须确认 | 必须 |
| 变更原因 | 触发调整的用户反馈或分析结论 | 必须 |
| 提出者 | 用户、Agent 或系统 | 必须 |
| 审批状态 | 待审批、已批准、已拒绝、已应用、已过期 | 必须 |
| 决策人和决策时间 | 谁何时批准或拒绝 | 有决策时记录 |

关键变化在批准前不能改变当前生效计划。

### 4.14 `Review`

| 属性 | 含义 | 要求 |
|---|---|---|
| 所属用户和计划 | 复盘归属 | 必须 |
| 时间范围 | 本次复盘覆盖的周期 | 必须 |
| 引用的计划版本 | 周期内实际生效过的版本 | 必须 |
| 原始任务和预计用时 | 计划基线 | 必须 |
| 实际完成情况 | 来自任务和跟进记录 | 必须 |
| 与计划差异 | 完成率、延期和未完成任务 | 必须 |
| 阻碍和原因 | 基于用户反馈总结 | 可用时记录 |
| 做得较好的部分 | 具体进展和有效行为 | 必须 |
| 下一阶段建议 | 是否需要调整计划 | 必须 |
| 生成时间 | 复盘产生时间 | 系统生成 |

复盘只能引用真实业务记录，不能只依赖聊天摘要。

复盘生成完成后可以触发候选洞察提取，但 `ProfileInsight` 是独立业务对象。洞察生成失败不会改变复盘状态，未确认洞察也不能回写或改写历史复盘。

### 4.15 `Conversation` 与 `Message`

| 对象 | 关键属性 |
|---|---|
| `Conversation` | 所属用户、关联目标、标题、创建时间、更新时间 |
| `Message` | 所属会话、角色、内容、创建时间、关联 Agent 执行 |

会话是交互记录，不是任务、审批或复盘的真实来源。

### 4.16 `Source`

| 属性 | 含义 | 要求 |
|---|---|---|
| 标题和 URL | 外部资料标识 | 必须 |
| 引用片段 | 回答实际使用的资料内容摘要 | 必须 |
| 获取时间 | 资料被发现的时间 | 必须 |
| 关联消息或工具调用 | 证明引用来源 | 必须 |

搜索结果属于不可信外部输入，不能因此绕过审批或直接触发修改计划。

### 4.17 `FollowUpSchedule` 与 `NotificationDelivery`

| 对象 | 关键属性 |
|---|---|
| `FollowUpSchedule` | 所属计划、跟进节奏、时区、首选渠道、备用渠道、免打扰时间、启用状态 |
| `NotificationDelivery` | 对应安排、发送渠道、计划发送时间、实际发送时间、尝试次数、状态、错误原因 |

跟进安排决定何时提醒；通知投递只记录实际发送结果。两者不决定任务是否完成。

### 4.18 `AgentRun` 与 `ToolCall`

| 对象 | 关键属性 |
|---|---|
| `AgentRun` | 所属用户、执行目的、模型、提示词版本、开始和结束时间、结果状态、关联会话 |
| `ToolCall` | 所属执行、工具名称、经过校验的参数、幂等键、执行结果、错误和耗时 |

这两类对象用于审计和排错，不能成为业务权限来源。

## 5. 所有权和可见范围

| 对象或操作 | 所有者 | 用户权限 | Agent 权限 | 定时任务权限 |
|---|---|---|---|---|
| 用户画像 | 用户本人 | 查看、修改、删除 | 读取，提出更新建议 | 读取跟进所需信息 |
| 画像事实 | 用户本人 | 查看、确认、修改、失效 | 提出候选事实 | 读取已确认事实 |
| 候选洞察 | 用户本人 | 查看证据、确认、拒绝、删除 | 生成候选、关联证据、执行评分 | 不可访问 |
| 洞察证据 | 洞察所属用户 | 查看引用依据 | 从当前用户记录中关联证据 | 不可访问 |
| 目标 | 用户本人 | 创建、暂停、完成 | 读取，提出修改建议 | 读取状态 |
| 计划草稿 | 用户本人 | 修改、确认、放弃 | 生成和编辑草稿 | 不可访问 |
| 生效计划 | 用户本人 | 查看、发起调整、批准关键变化 | 执行允许的低风险操作 | 读取跟进安排 |
| 计划版本 | 所属计划所有者 | 查看历史 | 读取，产生待确认版本 | 读取用于复盘和提醒 |
| 任务和依赖 | 所属计划所有者 | 创建、修改、更新进度 | 执行允许的更新，提出结构变化 | 只读取 |
| 跟进记录 | 用户本人 | 创建、查看、追加修正 | 读取用于分析和复盘 | 可创建提醒，不能伪造反馈 |
| 变更建议 | 用户本人 | 批准、拒绝、查看 | 提出建议 | 不可审批 |
| 复盘 | 用户本人 | 查看和请求重新生成 | 基于记录生成 | 可触发周期提醒 |
| 会话和消息 | 用户本人 | 查看和维护 | 在本次执行中使用 | 不可访问 |
| Agent 审计记录 | 用户本人 | 查看与其有关的安全摘要 | 追加执行记录 | 不可访问 |
| 其他用户数据 | 其他用户 | 禁止访问 | 禁止访问 | 禁止访问 |

权限规则：

1. 每一条业务记录都必须能够追溯到所有者。
2. 子对象权限不能与父对象所属用户冲突。
3. Agent 的权限不能超过发起本次请求的用户。
4. 系统内部任务也不能把不同用户的数据混入同一个模型上下文。

## 6. 关键不变量

以下规则无论通过界面、API、Agent 工具还是后台任务操作，都必须始终成立。

### 6.1 所有权和访问控制

1. 用户不能读取或修改其他用户的画像、目标、计划、任务、会话和复盘。
2. 每个任务必须属于一个计划，并属于该计划的所有者。
3. 不同用户的任务之间不能建立依赖关系。
4. Agent 只能访问发起当前任务所属用户的数据。

### 6.2 目标和计划

5. 同一目标同一时间最多只有一个生效计划。
6. 没有用户确认记录的版本不能成为生效计划。
7. 已确认的计划版本不可原地修改，只能产生新版本。
8. 每个新版本必须记录其基准版本或首次创建来源。
9. 用户拒绝的计划变更不能自动生效。
10. 关键变化在批准前不能改变当前生效计划。

### 6.3 任务和进度

11. 同一计划中的任务依赖不能形成循环。
12. 只有用户明确提交的反馈才能把任务标记为完成。
13. `TaskUpdate` 是进度变化的历史证据，不能被静默覆盖或删除。
14. 已提交的跟进记录如需纠正，只能追加修正记录。
15. 目标进度只根据当前生效计划中的有效任务计算，不能重复累计历史版本。

### 6.4 用户画像和候选洞察

16. 未确认的 `ProfileInsight` 不能进入正式用户画像。
17. 每条候选洞察必须关联可追溯的支持证据；存在矛盾记录时必须保留矛盾证据，洞察和证据必须属于同一用户。
18. 候选洞察是否达到确认门槛必须由确定性评分规则判断，不能只使用 LLM 自报的置信度。
19. 用户确认候选洞察后，系统才能创建或更新正式 `ProfileFact`，并保留两者的来源关系。
20. 用户拒绝的候选洞察不能被系统换一种表述反复推荐；新证据足以形成不同结论时除外。

### 6.5 对话、Agent 和外部资料

21. 对话内容本身不能直接等同于任务完成或计划审批。
22. 搜索结果不能直接触发修改计划等高权限操作。
23. Agent 工具调用必须经过参数、权限和状态校验。
24. 模型、搜索或工具失败不能留下虚假的成功状态或半完成数据。
25. Agent 不能根据敏感推断或身份评价决定计划和画像。

### 6.6 复盘和通知

26. 周复盘必须关联明确时间范围和该范围内实际生效的计划版本。
27. 复盘不能引用没有真实记录支持的任务完成情况。
28. 同一提醒不能因为后台重试而发送多次。
29. 通知失败不能改变任务和计划状态。

## 7. 计划版本规则

### 7.1 基本规则

- `Plan` 是长期容器，`PlanVersion` 是某一时刻的不可变结构快照。
- 用户编辑中的计划是草稿，草稿可以反复修改，不要求每次修改都产生正式版本。
- 用户第一次确认计划时产生 `V1`，并把它设为当前生效版本。
- 小范围自动调整通过校验后产生新版本，并记录自动调整原因。
- 关键变化先形成 `PlanChangeProposal`，批准后才产生新版本。
- 用户拒绝变更时，不产生新版本，原版本继续有效。
- 每个新版本必须记录基于哪个旧版本产生。
- 历史版本永久保留，不能被后续版本覆盖。
- 任务在多个版本之间尽量保留稳定标识，便于连续跟踪历史进度。
- 只是记录任务进度不会产生新的计划版本。
- 只有任务结构、排期或关键约束发生变化时才产生计划版本。
- 周复盘引用该周期内实际生效的版本，不自动引用当前最新版本。
- 如果目标范围或期望结果发生实质变化，应评估创建新的 `Goal`。

### 7.2 版本产生规则

| 操作 | 是否产生新版本 | 是否需要用户确认 |
|---|---:|---:|
| 草稿中调整任务描述 | 否 | 否 |
| 首次确认计划 | 是，`V1` | 是 |
| 调整同一天内的任务顺序 | 是，自动调整 | 否 |
| 调整下一次跟进时间 | 否 | 否 |
| 新增或删除任务 | 是 | 是 |
| 新增、跳过或删除阶段 | 是 | 是 |
| 延长或缩短截止日期 | 是 | 是 |
| 修改每周投入时间 | 是 | 是 |
| 改变目标岗位或求职范围 | 是，并评估是否创建新目标 | 是 |
| 用户提交任务进度 | 否 | 不适用 |
| 用户拒绝计划调整 | 否 | 不适用 |

### 7.3 版本结构一致性

- 每个生效版本必须能够明确指出当时的里程碑、任务、预计用时和依赖关系。
- 已删除的任务在历史快照中仍然可见。
- 新增任务不能出现在旧版本快照中。
- 修改任务预计用时属于计划结构调整，应产生新版本。
- 同一任务 ID 在不同版本中表示同一条工作的延续；任务被彻底删除后不再参与当前进度。

## 8. 进度计算规则

### 8.1 任务进度

- 未开始：`0%`
- 部分完成：使用用户最近一次有效提交的 `0%～99%` 进度
- 已完成：`100%`
- 受阻：保留原有进度，同时记录受阻状态和原因，不自动清零

任务当前进度来自最近一次有效的 `TaskUpdate`。历史更新不能被覆盖，调整进度时应在新的 `CheckIn` 中追加更新。

### 8.2 里程碑进度

里程碑进度根据其有效任务进行加权计算。已完成任务的权重按其预计用时计算；部分完成任务按已投入比例计算。

### 8.3 计划和目标进度

MVP 中，一个目标同一时间只有一个生效计划，因此目标进度可以使用当前生效计划的进度。

计算采用预计用时加权：

```text
计划进度 =
Σ(任务预计用时 × 任务进度)
/
Σ(任务预计用时)
```

示例：

- 任务 A 预计 2 小时，完成 100%；
- 任务 B 预计 6 小时，完成 50%。

```text
(2 × 100% + 6 × 50%) / (2 + 6)
= (200% + 300%) / 8
= 62.5%
```

边界规则：

- 没有预计用时的任务暂按权重 `1` 计算。
- 已取消或已从当前生效版本删除的任务不计入当前进度，但仍保留在历史版本中。
- 只计算当前生效计划中的有效任务，不把多个历史版本重复相加。
- 进度展示可以保留一位小数，内部不能因展示四舍五入而把未完成任务判定为完成。
- 当前计划没有有效任务时，进度显示为 `0%`，不能发生除零错误。
- Agent 可以解释计算结果，但不能自行编造进度数字。

### 8.4 进度的真实来源

任务进度的事实来源是用户提交的 `TaskUpdate`；里程碑、计划、目标进度都是计算结果。界面可以缓存计算结果，但不能让缓存替代历史记录。

## 9. 一个求职场景的对象流转示例

### 9.1 初始场景

用户想准备数据分析岗位求职，当前会 Python 基础，但缺少 SQL 项目经验，每周可投入 8 小时，希望两个月内开始投递。

### 9.2 对象流转

| 步骤 | 用户或系统动作 | 新增或修改对象 | 业务结果 |
|---|---|---|---|
| 1 | 用户注册并登录 | `User` | 建立账号和数据所有权 |
| 2 | 用户填写求职方向、技能和当前进展 | `UserProfile`、`ProfileFact` | 建立可确认的初步画像 |
| 3 | 用户输入“两个月内准备好数据分析岗求职” | `Goal` | 建立目标及时间和范围约束 |
| 4 | Agent 发现仍缺少目标岗位的具体级别和每周可投入时间，向用户追问 | `Conversation`、`Message` | 获取必要信息 |
| 5 | 用户确认目标为初级数据分析岗，每周投入 8 小时 | `ProfileFact` | 信息进入正式画像 |
| 6 | Agent 生成阶段、里程碑和任务 | `Plan`、`PlanVersion V1` 草稿、`Milestone`、`Task` | 形成可查看的计划草稿 |
| 7 | 用户确认计划 | `Plan`、`PlanVersion V1` | `V1` 成为当前生效版本 |
| 8 | 系统根据计划创建跟进安排 | `FollowUpSchedule` | 等待约定时间发送提醒 |
| 9 | 系统在约定时间通知用户 | `NotificationDelivery` | 用户收到进度确认提醒 |
| 10 | 用户提交“项目复盘完成 50%，SQL 未开始，周三只能投入 1 小时” | `CheckIn`、多条 `TaskUpdate` | 记录真实执行状态 |
| 11 | 目标进度按任务预计用时重新计算 | `Task` 当前进度、计划计算结果 | 展示加权后的实际进度 |
| 12 | Agent 发现本周可用时间明显减少，建议调整后续任务 | `PlanChangeProposal` | 关键变化等待用户批准 |
| 13 | 用户批准新的后续安排 | `PlanVersion V2` | 新版本生效，旧版本保留 |
| 14 | 周期结束，系统生成本周复盘 | `Review` | 复盘引用 `V1`、`V2`、跟进记录和任务差异 |
| 15 | 系统根据历史记录发现用户更适应短任务 | `ProfileInsight`、`InsightEvidence` | 形成候选规律并完成证据评分 |
| 16 | 周复盘展示证据，用户确认该偏好 | `ProfileInsight`、`ProfileFact` | 洞察被确认并进入正式画像 |
| 17 | 用户决定是否继续下一阶段 | `Review`、后续变更建议 | 根据用户意愿生成下一阶段计划 |

### 9.3 关键链路

```text
聊天消息表达意图
  → 画像事实保存用户情况
  → Goal 定义最终结果
  → Plan 组织执行方案
  → PlanVersion 保存已确认结构
  → Task 和 TaskUpdate 记录真实执行
  → PlanChangeProposal 处理计划变化
  → Review 基于真实记录生成复盘
  → ProfileInsight 从真实证据中发现候选规律
  → 用户确认后才进入 ProfileFact
```

对话负责理解用户意图，计划版本负责保存已确认方案，任务和跟进记录负责记录真实执行。任何复盘和 Agent 建议都必须能追溯回这些业务记录。
