# MyJARVIS 生命周期与状态机

本文件定义 MyJARVIS 各领域对象的状态、状态转换、触发者、前置条件和必要的副作用。

状态机描述业务规则，不规定数据库状态字段、API 路由或代码实现方式。

## 1. 生命周期设计原则

1. 每个对象只保存当前稳定状态，历史事实通过追加记录保存。
2. 状态转换必须由明确的用户命令、Agent 工具调用或系统事件触发。
3. 同一状态转换必须同时校验触发者、业务前置条件和用户权限。
4. 用户拥有计划激活和关键计划变化的最终确认权。
5. Agent 可以提出状态变化，但不能绕过关键审批。
6. 状态转换和重要副作用必须在同一事务中完成，不能只更新状态而遗漏通知、版本或关联记录。
7. 失败后必须保留可恢复状态，不能出现虚假的成功状态或半完成数据。
8. 终止状态不能被普通操作恢复；需要继续执行时应创建新的业务对象。
9. 状态名称用于表示稳定业务阶段，不能把时间派生条件混入状态。
10. 模型生成的内容必须经过结构和业务规则校验，不能自行决定高权限状态转换。

## 2. 状态、事件、派生条件和历史记录的区别

| 概念 | 含义 | 示例 |
|---|---|---|
| 状态 | 对象当前所处的稳定业务阶段 | 任务处于 `IN_PROGRESS` |
| 事件或命令 | 触发对象变化的行为 | 用户提交计划确认、Worker 开始发送通知 |
| 派生条件 | 根据数据和时间实时计算，不稳定保存为生命周期状态 | `overdue`、`at_risk` |
| 历史记录 | 已经发生、后续只能追加或替代的事实 | `Message`、`CheckIn`、`TaskUpdate` |

### 2.1 不作为状态的值

- `PARTIAL` 不作为任务状态。它表示任务进度位于 `1%～99%`。
- `OVERDUE` 不作为任务状态。它由截止时间与当前时间计算。
- `AT_RISK` 不作为计划状态。它由进度、剩余时间和阻碍计算。
- `READ` 不作为通知状态。用户是否已读由独立阅读记录表达。
- 模型输出的置信度不能直接成为业务状态，必须经过结构化证据评分。

### 2.2 历史记录和确认记录

- `CheckIn`、`TaskUpdate`、`Message` 和 `Source` 是追加型历史记录。
- 历史记录提交后不能静默覆盖；需要修正时追加新的修正记录。
- 计划审批、画像确认和变更拒绝必须保留确认人、确认时间和当时的证据。

## 4. ProfileFact 状态机

`ProfileFact` 表示个人画像中一条具有来源和确认状态的业务事实。

### 4.1 状态转换

| 当前状态 | 命令或事件 | 触发者 | 前置条件 | 下一状态 | 副作用 |
|---|---|---|---|---|---|
| 无 | 用户直接填写或明确陈述信息 | 用户 | 内容清楚且格式合法 | `CONFIRMED` | 更新当前画像，保存来源 |
| 无 | 从模糊对话中提取信息 | Agent | 能关联原始消息 | `PENDING_CONFIRMATION` | 展示待确认信息 |
| 无 | 用户确认一条 `ProfileInsight` | 用户 | 洞察处于 `CONFIRMATION_REQUESTED` | `CONFIRMED` | 记录来源洞察和证据 |
| `PENDING_CONFIRMATION` | 用户确认 | 用户 | 内容未被新值替代 | `CONFIRMED` | 更新当前画像 |
| `PENDING_CONFIRMATION` | 用户拒绝 | 用户 | 无 | `REJECTED` | 不再作为画像事实 |
| `CONFIRMED` | 保存同一信息的新值 | 用户 | 新值有效 | 旧记录变 `SUPERSEDED` | 新值成为当前画像事实 |
| 任意非删除状态 | 用户删除 | 用户 | 无 | `DELETED` | 从当前画像移除，保留必要审计信息 |

### 4.2 规则

- 用户直接、明确表达的信息可以直接成为 `CONFIRMED`。
- 模糊提取、存在歧义或与既有画像冲突的信息进入 `PENDING_CONFIRMATION`。
- 性格、心理状态和其他敏感推断不能直接创建为正式 `ProfileFact`。
- 被拒绝、替代或删除的事实不能参与当前个性化。
- `ProfileFact` 不负责保存完整的规律发现和证据评分过程；这部分由 `ProfileInsight` 负责。

## 5. ProfileInsight 状态机

`ProfileInsight` 表示系统根据对话、任务历史、跟进记录和用户选择形成的候选个性化规律。

例如：

> 最近多次记录显示，用户更容易完成 30～45 分钟的小任务。

候选洞察描述的是可观察行为及其适用条件，不是“懒惰”“内向”等身份标签。

### 5.1 状态转换

| 当前状态 | 命令或事件 | 触发者 | 前置条件 | 下一状态 | 副作用 |
|---|---|---|---|---|---|
| 无 | 周复盘发现候选规律 | 系统/Agent | 至少存在一条可关联证据 | `CANDIDATE` | 保存候选结论和证据关系 |
| 无 | 用户主动要求记住明确偏好 | 用户 | 内容清楚 | 不创建洞察，直接创建 `ProfileFact` | 更新正式画像 |
| `CANDIDATE` | 证据评分达到阈值 | 确定性评分服务 | 满足全部硬性门槛 | `SUPPORTED` | 保存分数和评分明细 |
| `CANDIDATE` | 长期没有新增证据 | 系统 | 超过有效期 | `EXPIRED` | 不再使用该候选规律 |
| `SUPPORTED` | 在周复盘或其他合适时机询问用户 | 系统 | 不在询问冷却期 | `CONFIRMATION_REQUESTED` | 记录提示时间，限制批量提示数量 |
| `CONFIRMATION_REQUESTED` | 用户确认 | 用户 | 依据仍然有效 | `USER_CONFIRMED` | 创建或更新对应 `ProfileFact` |
| `CONFIRMATION_REQUESTED` | 用户拒绝 | 用户 | 无 | `REJECTED` | 阻止相同结论重复提示 |
| `CONFIRMATION_REQUESTED` | 证据过期 | 系统 | 超过有效期 | `EXPIRED` | 取消待确认提示 |
| `USER_CONFIRMED` | 用户修改偏好或出现新版本 | 用户 | 新结论有效 | `SUPERSEDED` | 旧洞察保留，正式画像使用新事实 |

用户未回应确认提示时，洞察可以保持 `CONFIRMATION_REQUESTED`，但必须记录最近提示时间并遵守冷却期，不能反复打扰。

### 5.2 证据评分

证据分用于判断“是否值得询问用户”，不代表用户性格判断的概率。

LLM 负责寻找可能规律并说明支持证据；分数必须由确定性代码根据结构化数据计算。

建议评分维度：

| 维度 | 分值 | 规则示例 |
|---|---:|---|
| 支持次数 | 30 | 5 条以上 30 分；3～4 条 20 分；少于 3 条不能标记为 `SUPPORTED` |
| 跨场景程度 | 20 | 至少跨 2 个日期或场景 20 分；仅一个场景 10 分 |
| 一致性 | 20 | 根据支持证据和矛盾证据比例计算 |
| 时效性 | 15 | 最近 7 天 15 分；30 天内 10 分；60 天内 5 分 |
| 明确程度 | 15 | 主要来自重复行为 10 分；有补充明确表达 15 分 |

建议初始阈值：

- 总证据分达到 `70` 分才进入 `SUPPORTED`。
- 至少 3 条支持证据。
- 证据至少来自 2 个不同日期或场景。
- 每条证据必须关联到消息、`CheckIn`、`TaskUpdate` 或其他真实业务记录。
- 用户已经拒绝过的相同结论不能再次自动推荐。
- 禁止推断心理疾病、敏感身份或带有评价性的人格标签。
- 关键计划条件，例如截止日期和可投入时间，不能仅凭行为推断，必须由用户确认。

阈值是产品参数，应通过固定测试数据验证和调整，不能把 `70` 分解释为“70% 的人格概率”。

### 5.3 候选洞察的展示规则

- 一次周复盘默认最多展示 1～3 条候选洞察。
- 同一维度一次只展示一个候选结论。
- 展示结论时必须能展开查看支持证据和矛盾证据。
- 用户可以确认、拒绝或选择“仅在当前计划使用”。
- “仅在当前计划使用”不创建正式 `ProfileFact`。
- 用户拒绝后至少 30 天内不重复询问；除非用户明确改变了偏好，否则不再主动推荐相同结论。
- 用户确认后，仍可在个人画像中修改、删除或关闭该偏好的使用。

## 6. Goal 状态机

### 6.1 状态转换

| 当前状态 | 命令或事件 | 触发者 | 前置条件 | 下一状态 | 副作用 |
|---|---|---|---|---|---|
| 无 | 创建目标 | 用户 | 有明确期望结果 | `ACTIVE` | 建立目标所有权 |
| `ACTIVE` | 暂停目标 | 用户 | 无 | `PAUSED` | 暂停关联计划和跟进安排 |
| `PAUSED` | 恢复目标 | 用户 | 无 | `ACTIVE` | 按用户选择恢复计划 |
| `ACTIVE` / `PAUSED` | 完成目标 | 用户 | 用户明确确认 | `COMPLETED` | 结束当前执行周期 |
| `ACTIVE` / `PAUSED` | 取消目标 | 用户 | 用户明确确认 | `CANCELLED` | 取消关联计划和待发送通知 |

### 6.2 规则

- `COMPLETED` 和 `CANCELLED` 是终止状态。
- 系统可以提示目标可能已经具备完成条件，但不能自动完成。
- 完成目标前，必须处理未完成任务；未完成任务不能被静默标记为完成。
- 取消目标后保留历史数据，后续继续行动需要创建新的目标。

## 7. Plan 状态机

### 7.1 状态转换

| 当前状态 | 命令或事件 | 触发者 | 前置条件 | 下一状态 | 副作用 |
|---|---|---|---|---|---|
| 无 | 创建计划草稿 | 用户/Agent | 存在目标且上下文合法 | `DRAFT` | 创建首个草稿版本 |
| `DRAFT` | 用户确认计划 | 用户 | 存在合法草稿版本；同目标无其他生效计划 | `ACTIVE` | 激活版本并创建跟进安排 |
| `ACTIVE` | 暂停计划 | 用户 | 无 | `PAUSED` | 暂停跟进安排 |
| `PAUSED` | 恢复计划 | 用户 | 目标未暂停或取消 | `ACTIVE` | 重新计算下一次跟进时间 |
| `ACTIVE` / `PAUSED` | 确认完成计划 | 用户 | 用户明确确认 | `COMPLETED` | 结束跟进安排 |
| `DRAFT` / `ACTIVE` / `PAUSED` | 取消计划 | 用户 | 用户明确确认 | `CANCELLED` | 取消跟进和待发送通知 |

### 7.2 规则

- 草稿计划不能发送跟进提醒。
- 同一目标同一时间最多存在一个 `ACTIVE` 或 `PAUSED` 的计划。
- 激活计划必须同时激活一个合法的 `PlanVersion`。
- 计划暂停时允许用户主动提交进度，但不发送新提醒。
- `COMPLETED` 和 `CANCELLED` 是终止状态。

## 8. PlanVersion 状态机

### 8.1 状态转换

| 当前状态 | 命令或事件 | 触发者 | 前置条件 | 下一状态 | 副作用 |
|---|---|---|---|---|---|
| 无 | 创建首个草稿版本 | 用户/Agent | 计划处于草稿状态 | `DRAFT` | 保存可编辑结构 |
| 无 | 生成计划调整版本 | Agent/系统 | 变更已经批准或属于低风险自动调整 | `DRAFT` | 保存基准版本和变更原因 |
| `DRAFT` | 用户确认首个版本 | 用户 | 结构和权限合法 | `ACTIVE` | 计划进入执行 |
| `DRAFT` | 应用自动调整或已批准变更 | 系统 | 基准版本仍为当前版本 | `ACTIVE` | 旧生效版本变 `SUPERSEDED` |
| `DRAFT` | 放弃版本 | 用户/系统 | 已被替代或计划取消 | `DISCARDED` | 保留变更原因 |
| `ACTIVE` | 新版本生效 | 系统 | 新版本合法 | `SUPERSEDED` | 保留历史快照 |

### 8.2 版本激活的不变量

任何版本切换必须在同一事务中保证：

```text
旧生效版本 ACTIVE → SUPERSEDED
新版本 DRAFT → ACTIVE
Plan.current_version 指向新版本
基于旧版本的其他待审批建议 EXPIRED
```

一个计划最多只有一个 `ACTIVE` 版本。已生效版本不能重新激活或原地修改。

## 9. Milestone 状态机

### 9.1 状态转换

| 当前状态 | 命令或事件 | 触发者 | 前置条件 | 下一状态 | 副作用 |
|---|---|---|---|---|---|
| 无 | 计划生效并创建里程碑 | 系统 | 版本合法 | `NOT_STARTED` | 建立任务关系 |
| `NOT_STARTED` | 任一有效任务开始或进度大于 0 | 系统 | 计划允许更新 | `IN_PROGRESS` | 更新阶段展示 |
| `IN_PROGRESS` | 所有有效任务完成 | 系统 | 无未完成任务 | `COMPLETED` | 重新计算计划进度 |
| `COMPLETED` | 用户明确重新打开任务 | 用户 | 修正记录有效 | `IN_PROGRESS` | 撤销阶段完成结果 |
| 任意非取消状态 | 已批准计划变更取消该里程碑 | 系统 | 变更已应用 | `CANCELLED` | 保留任务历史 |

### 9.2 规则

- 里程碑状态主要由任务状态计算。
- 任务受阻不自动产生独立的里程碑状态，只形成风险提示。
- 阶段完成不等于目标完成。
- 已取消的里程碑不能自动恢复。

## 10. Task 状态机

### 10.1 状态转换

| 当前状态 | 命令或事件 | 触发者 | 前置条件 | 下一状态 | 副作用 |
|---|---|---|---|---|---|
| 无 | 生效计划创建任务 | 系统 | 版本合法 | `TODO` | 初始化进度为 0 |
| `TODO` | 用户报告 1%～99% | 用户 | 计划允许更新 | `IN_PROGRESS` | 追加 `TaskUpdate` |
| `IN_PROGRESS` | 用户报告 0% | 用户 | 明确提交 | `TODO` | 追加 `TaskUpdate` |
| `TODO` / `IN_PROGRESS` | 用户报告受阻 | 用户 | 有阻碍说明或明确选择 | `BLOCKED` | 保留当前进度并追加记录 |
| `BLOCKED` | 用户恢复处理 | 用户 | 明确提交 | `TODO` / `IN_PROGRESS` | 追加恢复记录 |
| 任意未完成状态 | 用户报告 100% | 用户 | 明确提交 | `DONE` | 进度变 100%，重算里程碑 |
| `DONE` | 用户纠正并重新打开 | 用户 | 明确提交 | `IN_PROGRESS` | 追加修正记录 |
| 任意非终止状态 | 已批准计划变更删除任务 | 系统 | 变更已应用 | `CANCELLED` | 保留历史并重新计算进度 |

### 10.2 规则

- `DONE` 必须同时满足进度为 `100%`。
- `1%～99%` 使用 `IN_PROGRESS` 和进度值表达，不新增 `PARTIAL` 状态。
- 任务受阻时不得清零已有进度。
- 逾期是根据截止日期和当前时间计算的派生条件。
- 已取消任务不能直接重新打开；需要新的、经批准的计划版本恢复。
- 只有用户明确提交的反馈才能将任务标记完成。

## 11. PlanChangeProposal 状态机

### 11.1 状态转换

| 当前状态 | 命令或事件 | 触发者 | 前置条件 | 下一状态 | 副作用 |
|---|---|---|---|---|---|
| 无 | 创建关键变更建议 | Agent/用户 | 触及关键字段 | `PENDING_APPROVAL` | 保存基准版本和差异 |
| 无 | 创建低风险自动调整 | Agent/系统 | 未触及关键字段 | `APPLIED` | 立即创建并激活新版本 |
| `PENDING_APPROVAL` | 用户批准并应用 | 用户 | 基准版本仍然有效 | `APPLIED` | 新版本生效，旧版本替代 |
| `PENDING_APPROVAL` | 用户拒绝 | 用户 | 无 | `REJECTED` | 当前计划保持不变 |
| `PENDING_APPROVAL` | 基准版本已失效 | 系统 | 计划已有新版本 | `EXPIRED` | 禁止继续应用旧方案 |

### 11.2 关键变化

以下变化必须经过用户确认：

- 新增或删除任务。
- 新增、跳过或删除阶段。
- 修改截止日期。
- 修改每周投入时间。
- 修改目标岗位或求职范围。
- 减少、跳过或替换关键里程碑。

以下变化可以作为低风险自动调整：

- 在不改变阶段和期限的情况下调整任务顺序。
- 在同一天内重新分配小范围任务。
- 调整下一次跟进时间。

### 11.3 批准与应用

用户批准和实际应用应在同一个事务中完成。事务失败时建议保持 `PENDING_APPROVAL`，不能显示为已应用。

## 12. FollowUpSchedule 状态机

### 12.1 状态转换

| 当前状态 | 命令或事件 | 触发者 | 前置条件 | 下一状态 | 副作用 |
|---|---|---|---|---|---|
| 无 | 生效计划创建跟进安排 | 系统 | 用户已设置或接受默认偏好 | `ACTIVE` | 计算下一次提醒时间 |
| `ACTIVE` | 暂停计划 | 用户 | 无 | `PAUSED` | 停止产生新通知 |
| `PAUSED` | 恢复计划 | 用户 | 计划已恢复 | `ACTIVE` | 重新计算提醒时间 |
| `ACTIVE` | 计划完成 | 系统 | 无 | `COMPLETED` | 不再产生提醒 |
| `ACTIVE` / `PAUSED` | 计划取消 | 系统 | 无 | `CANCELLED` | 取消待发送通知 |
| `ACTIVE` | 用户稍后提醒 | 用户 | 有新的提醒时间 | 保持 `ACTIVE` | 修改 `next_due_at` |

### 12.2 规则

- “稍后提醒”是修改下一次到期时间，不是状态。
- 跟进安排遵循用户时区和免打扰时间。
- 一个跟进安排只能属于一个计划和一个用户。

## 13. NotificationDelivery 状态机

### 13.1 状态转换

| 当前状态 | 命令或事件 | 触发者 | 前置条件 | 下一状态 | 副作用 |
|---|---|---|---|---|---|
| 无 | 到达提醒时间 | 定时任务 | 跟进安排有效 | `PENDING` | 创建唯一投递记录 |
| `PENDING` | Worker 取得发送权 | 系统 | 未超过最大尝试次数 | `SENDING` | 设置发送租约 |
| `SENDING` | 渠道发送成功 | 系统 | 收到成功结果 | `SENT` | 记录发送时间 |
| `SENDING` | 出现可重试错误 | 系统 | 未超过最大次数 | `RETRYING` | 记录错误和下次重试时间 |
| `RETRYING` | 到达重试时间 | 系统 | 原通知仍有效 | `SENDING` | 重新取得发送权 |
| `SENDING` / `RETRYING` | 超过最大尝试次数 | 系统 | 无 | `FAILED_PERMANENTLY` | 尝试备用渠道并告警 |
| `PENDING` | 计划暂停或取消 | 系统 | 尚未发送 | `CANCELLED` | 不再发送该通知 |

### 13.2 恢复规则

- `SENDING` 必须包含租约截止时间。
- Worker 崩溃后，租约过期的投递任务可以恢复为 `PENDING`。
- 恢复和重试必须使用幂等键，不能让一次提醒变成多次业务提醒。
- `SENT` 只表示渠道接受发送请求，不表示用户已读。

## 14. Review 状态机

### 14.1 状态转换

| 当前状态 | 命令或事件 | 触发者 | 前置条件 | 下一状态 | 副作用 |
|---|---|---|---|---|---|
| 无 | 请求周期复盘 | 用户/定时任务 | 时间范围和计划版本明确 | `GENERATING` | 收集任务和跟进证据 |
| `GENERATING` | 生成成功 | 系统 | 内容和引用完整 | `READY` | 保存不可变复盘结果 |
| `GENERATING` | 生成失败或超时 | 系统 | 输出无效或超时 | `FAILED` | 保留失败原因，允许重试 |
| `READY` | 同一周期重新生成复盘 | 用户/系统 | 用户明确请求或规则允许 | 旧复盘 `SUPERSEDED` | 新复盘进入 `GENERATING` |

### 14.2 周复盘和画像洞察

周复盘可以触发画像洞察提取，但两个过程职责分离：

```text
Review GENERATING
  → Review READY
  → 触发生成或更新 ProfileInsight
  → ProfileInsight CANDIDATE
  → 证据评分
  → 达到阈值后 SUPPORTED
  → 周复盘中询问用户
```

规则：

- `Review READY` 不依赖画像洞察是否生成成功。
- 洞察提取失败不能使复盘失败，也不能修改正式画像。
- 周复盘最多集中展示 1～3 条候选洞察。
- 复盘正文和候选洞察建议应分开显示，避免把未经确认的推断写成已经成立的事实。
- 用户确认洞察后创建或更新 `ProfileFact`，但不回写或改写历史复盘。

## 15. 跨对象联动规则

### 15.1 用户确认计划

```text
Plan DRAFT → ACTIVE
PlanVersion DRAFT → ACTIVE
FollowUpSchedule 创建或进入 ACTIVE
```

同时必须保证计划属于当前用户、目标合法且没有其他生效计划。

### 15.2 小范围自动调整

```text
PlanChangeProposal → APPLIED
旧 PlanVersion ACTIVE → SUPERSEDED
新 PlanVersion DRAFT → ACTIVE
Plan.current_version 指向新版本
基于旧版本的待审批建议 → EXPIRED
```

### 15.3 计划暂停

```text
Plan ACTIVE → PAUSED
FollowUpSchedule ACTIVE → PAUSED
尚未发送的 NotificationDelivery → CANCELLED
```

暂停不阻止用户主动更新任务，但不再自动产生新的提醒。

### 15.4 计划恢复

```text
Plan PAUSED → ACTIVE
FollowUpSchedule PAUSED → ACTIVE
重新计算下一次提醒时间
```

### 15.5 用户提交任务更新

```text
CheckIn 创建
TaskUpdate 追加
Task 状态和进度更新
Milestone 状态重新计算
Plan 检查是否具备完成条件，但不自动完成
```

### 15.6 用户确认画像洞察

```text
ProfileInsight CONFIRMATION_REQUESTED → USER_CONFIRMED
创建或更新 ProfileFact → CONFIRMED
保存 ProfileFact 与 ProfileInsight 的来源关系
```

### 15.7 用户拒绝画像洞察

```text
ProfileInsight CONFIRMATION_REQUESTED → REJECTED
正式画像保持不变
记录拒绝时间和提示冷却期
```

### 15.8 用户批准关键计划变更

```text
校验 Proposal 基准版本仍有效
新 PlanVersion 生效
旧 PlanVersion SUPERSEDED
Proposal APPLIED
基于旧版本的其他待审批建议 EXPIRED
```

## 16. 失败、重试与恢复

### 16.1 通用失败规则

- 模型调用失败不能改变任务、计划或画像状态。
- 搜索失败不能生成虚构来源。
- Agent 工具参数校验失败不能执行数据库写入。
- 状态转换事务失败时，应保持转换前状态。
- 后台任务必须带幂等键，重试不能制造重复业务记录。

### 16.2 可恢复失败

| 场景 | 恢复方式 |
|---|---|
| 计划确认时创建跟进安排失败 | 整个事务回滚，计划保持 `DRAFT` |
| 计划版本切换失败 | 旧版本保持 `ACTIVE`，新版本保持 `DRAFT` |
| 周复盘生成失败 | `Review` 保持 `FAILED`，允许重试 |
| 候选洞察评分失败 | 洞察保持 `CANDIDATE`，不向用户确认 |
| 通知发送失败 | 按退避策略重试，必要时切换备用渠道 |
| Worker 在发送中崩溃 | 租约过期后恢复投递 |

### 16.3 终止失败

通知超过最大重试次数后进入 `FAILED_PERMANENTLY`，保留失败原因并触发后台告警。

计划或目标处于终止状态后，不再自动恢复；用户需要创建新的计划或目标继续执行。

## 17. 状态转换验收场景

以下场景应能够转化为后续自动化测试。

### 17.1 计划确认

1. 计划只有草稿版本时，用户确认后进入 `ACTIVE`。
2. 无合法版本、无用户确认或同目标已有生效计划时，确认失败。
3. 跟进安排创建失败时，计划不能单独进入 `ACTIVE`。

### 17.2 关键变化审批

1. 用户拒绝计划变更后，当前版本保持不变。
2. 用户批准的计划变更产生新版本，旧版本变 `SUPERSEDED`。
3. 基于旧版本的待审批建议自动进入 `EXPIRED`。

### 17.3 任务和里程碑

1. 任务从 `TODO` 更新至 50% 后进入 `IN_PROGRESS`。
2. 任务报告受阻后保留原进度并进入 `BLOCKED`。
3. 所有任务完成后，里程碑自动进入 `COMPLETED`。
4. 重新打开已完成任务后，里程碑回到 `IN_PROGRESS`。

### 17.4 画像洞察

1. 少于 3 条支持证据的洞察不能进入 `SUPPORTED`。
2. 分数组件必须完整保存，不能只保存 LLM 给出的总分。
3. 达到阈值后，周复盘可以询问用户是否加入画像。
4. 用户拒绝后，相同洞察不能立即重复询问。
5. 用户确认后创建 `ProfileFact`，并保留来源洞察和证据。
6. 未确认的画像洞察不能参与正式用户画像。

### 17.5 通知和复盘

1. 计划暂停后，尚未发送的通知被取消。
2. Worker 重试后，同一次提醒不能生成多个逻辑业务提醒。
3. 周复盘生成失败不能修改任务和画像。
4. 洞察提取失败不能使已经生成的周复盘失效。
