# MyJARVIS 产品规格

## 1. 产品定义

- 一句话定位：一个能够了解用户情况、制定可执行计划并持续跟进执行过程的个人成长与决策助手。
- 主要用户：希望借助 AI 制定和执行求职、学习等计划的自我提升人群。
- 用户核心痛点：普通 LLM 可以实现简单的问答和计划制定，但无法建立可持续使用的用户画像，也无法对计划的执行情况进行长期跟进，并根据真实反馈调整计划。
- MVP 演示领域：用户想要求职，系统根据用户的实际情况制定计划，持续跟进计划执行情况，并进行动态调整。
- 用户最终获得的价值：一个真正了解自己的目标、约束和执行情况，并能帮助自己持续行动的成长与决策平台。

## 2. 核心场景

### 场景一：创建并确认计划

- 触发条件：用户明确提出需要制定一个计划
- 用户输入：根据我的实际情况，帮我制定一个求职计划
- Agent 需要了解的信息：用户已经掌握的技术栈、求职方向、目前缺少的技术栈、目标岗位、截止时间和每周可投入时间。已经记录在用户画像中的信息不再重复询问。
- Agent 输出：先与用户确认必要信息，再生成一份结构清晰、可以立即开始执行的计划草稿。计划需要包含阶段、里程碑、具体任务、预计用时、任务依赖和完成标准。
- 用户确认操作：计划草稿保存后不会自动生效。用户可以在专门的计划界面查看完整内容；确认后计划才进入执行状态，并启用后续跟进。如果用户不确认，可以根据反馈继续修改草稿。
- 系统创建的数据：目标、计划草稿、计划版本；用户确认后，创建或启用里程碑、任务和跟进安排。用户及其基础资料在开始制定计划前已经存在。

### 场景二：主动跟进

- 触发条件：用户确认计划后，根据用户设定的跟进时间和通知偏好进行定时询问。
- 提醒内容：询问今天的任务完成情况、是否遇到阻碍，以及下一次可投入的时间是否发生变化。
- 用户可选择的反馈：已完成、部分完成、未开始、遇到阻碍，并可以补充文字说明。
- 系统如何处理反馈：记录用户反馈和反馈时间，根据用户明确提交的结果更新任务状态和整体进度。Agent 不能仅根据聊天内容猜测任务已经完成。
- 其他要求：用户可以设置免打扰时段；通知失败时应使用备用通知渠道，同一个提醒不能重复发送多次。

### 场景三：计划调整

- 什么情况触发调整：
  - 周复盘时发现本周用户完成情况明显偏离计划，主动询问用户是否需要调整。
  - 用户主动提出需要调整计划。
  - 用户反馈可用时间、任务依赖或目标情况发生变化。
- 哪些调整可以自动执行：只允许在当前阶段和执行期限不变的前提下调整低风险内容，例如任务顺序、同一天内的小范围任务安排和下一次跟进时间。
- 哪些调整必须确认：新增或删除任务、改变截止日期、改变每周投入时间、改变目标或岗位范围、减少或跳过关键阶段。
- 用户拒绝后如何处理：默认保持当前计划不变，询问用户拒绝原因，并允许用户选择继续原计划、只修改具体任务或结束本次调整。不能陷入反复提出同一调整方案的循环。

### 场景四：周复盘

- 本周期需要记录的数据：当前计划版本中的原始任务和预计用时、任务实际完成情况、每次跟进反馈、延期记录、用户报告的阻碍、可用时间变化和本周期内发生的计划调整。
- 周复盘包含的内容：实际完成情况与原始计划的差异、主要原因、做得较好的部分、需要解决的问题，以及下一周期的建议。如果差异较大，询问用户是否需要调整计划；如果执行情况良好，对具体进步给予反馈。
- 下一阶段计划如何产生：根据任务完成情况询问用户意愿。用户同意后，系统基于当前画像、复盘结果和剩余目标生成下一阶段计划草稿，用户确认后生效。

## 3. MVP 范围

### 必须实现

- 建立可持续使用、对用户可见且可编辑的长期用户画像，包括技术栈、求职方向、目标岗位、时间约束和求职进展。
- Agent 可以根据用户提供的信息提出画像更新建议，但新增的长期记忆需要用户可见，用户能够修改或删除。
- 计划的创建、草稿确认、执行、主动跟进和动态调整。
- 区分自动执行的小范围调整与需要用户批准的关键变化，并保留计划版本和调整记录。
- 任务进度、阻碍和周复盘的记录与展示。
- 方便手机使用的可视化计划界面，以及 PWA 安装能力。
- 搜索资料并在回答中展示来源引用。
- PWA 推送和邮件兜底提醒。

### MVP 暂不实现

- 原生 iOS/Android App。
- 完整的飞书小程序和管理后台。
- 日历双向同步。
- 多 Agent 自动协作。
- 语音交互。
- 付费、订阅和商业化功能。
- 企业管理员后台。
- 未经过用户确认的隐式长期记忆和敏感推断。

## 4. 用户角色

- 访客：可以查看产品介绍和注册登录入口；不能调用大模型、录入个人资料或访问业务数据。
- 已登录用户：只能访问自己的画像、目标、计划、任务、会话和复盘，拥有计划激活及关键变化的最终确认权。
- Agent：受后端约束的系统执行者。可以读取当前用户上下文、搜索资料、更新进度、提出计划调整，但不能绕过用户批准关键变化，也不能直接执行任意数据库操作。
- 定时任务系统：按照用户确认的计划和通知偏好发送跟进提醒，决定何时提醒，但不由 LLM 随意决定是否发送。
- 管理员：MVP 暂不实现。

| 操作 | 访客 | 已登录用户 | Agent | 定时任务系统 |
|---|---|---|---|---|
| 注册和登录 | 是 | 是 | 否 | 否 |
| 查看个人画像和计划 | 否 | 仅自己的数据 | 仅当前用户上下文 | 否 |
| 生成计划草稿 | 否 | 发起 | 生成结构化草稿 | 否 |
| 激活计划 | 否 | 是 | 否 | 否 |
| 小范围调整计划 | 否 | 可发起 | 可提出或执行允许的操作 | 否 |
| 关键计划变化 | 否 | 最终批准 | 只能提出建议 | 否 |
| 发送跟进提醒 | 否 | 设置时间和偏好 | 否 | 按计划和偏好执行 |

## 5. 核心业务规则

- 所有业务数据必须属于当前登录用户，用户不能访问其他用户的数据。
- 计划草稿和生效计划是两个不同状态；只有用户确认后才能激活并创建跟进安排。
- 用户明确提交的任务结果和进度是更新任务状态的主要依据，Agent 不能擅自把任务标记为完成。
- 关键变化必须由用户确认，未经确认时原计划继续有效。
- 每次计划调整都要保留修改前、修改后、原因和确认结果。
- 周复盘必须基于计划版本、任务记录和用户反馈，不能只依赖模型对聊天内容的回忆。
- 搜索内容属于不可信外部信息，只能作为参考资料，不能直接触发修改计划等敏感操作。
- 长期画像中的信息必须对用户可见、可编辑，未经用户确认不保存敏感推断。
- 通知遵循用户时区、通知渠道和免打扰设置，同一个提醒不能重复发送。

## 6. 成功标准

- 用户可以在 iPhone PWA 上完成注册、补充画像、输入求职目标并获得计划草稿。
- 用户能够查看、修改和确认计划；确认后计划进入执行状态并创建后续跟进。
- 用户能够收到至少一种主动提醒，并通过提醒或应用记录任务进度和阻碍。
- 用户报告时间变化或出现明显延期时，系统能区分小范围调整和关键变化。
- 小范围调整能够自动完成，关键变化必须等待用户确认，拒绝后原计划保持不变。
- 系统能够基于真实执行记录生成周复盘，并包含与原始计划的差异和下一步建议。
- 搜索类回答能够展示来源；模型或搜索失败时不会错误更新计划或任务状态。
- 用户无法访问其他用户的个人资料、计划、任务、会话或复盘。

## 7. 失败与异常场景

- 模型调用失败时：保留用户已经输入的内容，明确提示本次生成失败并允许重试；不能显示虚假的成功状态，也不能留下未完成的数据。
- 搜索失败时：可以基于当前用户资料和已有信息继续回答，但必须说明本次搜索不可用；涉及实时信息时不能编造来源。
- 通知发送失败时：自动尝试备用通知渠道，记录失败原因并向后台告警；应用内保留对应待办。
- 用户长期不反馈时：按固定规则降低提醒频率，将多次提醒合并为摘要，并允许用户暂停计划；不能通过模型生成带有施压、羞辱或操纵性的内容。
- 计划无法在截止日期前完成时：向用户展示无法完成的具体原因和可选方案，由用户确认是否延长截止日期、减少范围或调整投入时间。
- 用户拒绝关键调整时：原计划继续有效，系统只记录拒绝原因，不自动寻找其他理由再次修改。
